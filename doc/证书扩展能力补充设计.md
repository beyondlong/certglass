# CertGlass 证书扩展能力补充设计

## 1. 目标与现状

本设计补充 CertGlass 的“详细信息”能力，使其达到 Windows 证书查看器常用字段的可读性，同时保留 macOS 原生、只读、离线和不丢失原始值的定位。

当前脚手架已经具备以下基础：

- `CertificateExtension` 保留扩展 OID、critical 和原始 `extnValue` 内容。
- `CertificateField` 支持中文名、英文名、OID、critical、格式化值和十六进制原始值。
- 解析器已经对 Basic Constraints、Key Usage、Extended Key Usage 做了初步文本化。
- 详细信息页目前是可搜索的平铺列表，点击字段后没有独立的详细解释区域。

当前主要缺口：

- 常用扩展的语义不完整，Key Usage 仍显示英文标识，无法直接看懂“数字签名、密钥加密、数据加密”等用途。
- SAN、SKI、AKI、CRL Distribution Points、AIA、Certificate Policies、Name Constraints 等扩展还没有结构化中文解释。
- 未知或非关键扩展虽然能看到 OID 和十六进制值，但没有“这是原始值、应用没有猜测其语义”的明确说明，也没有结构化的详细值查看。
- 详情页缺少 Windows 式的“字段列表 + 选中字段详细内容”交互。

## 2. 产品范围

首期按推荐范围覆盖 RFC 5280 中最常用的标准扩展，并为所有其他扩展提供安全的原始展示。

### 2.1 首期必须结构化解释的扩展

| OID | 中文名称 | RFC 5280 | 展示重点 |
| --- | --- | --- | --- |
| `2.5.29.19` | 基本约束 | 4.2.1.9 | 是否 CA、路径长度限制 |
| `2.5.29.15` | 密钥用法 | 4.2.1.3 | 每个 bit 的中文用途、原始 bit 状态 |
| `2.5.29.37` | 扩展密钥用法 | 4.2.1.12 | 每个用途 OID、标准名称和中文解释 |
| `2.5.29.17` | 主题备用名称 | 4.2.1.6 | DNS、IP、邮箱、URI、注册 ID 等类型和值 |
| `2.5.29.14` | 主题密钥标识符 | 4.2.1.2 | 十六进制标识符及字节数 |
| `2.5.29.35` | 颁发机构密钥标识符 | 4.2.1.1 | keyIdentifier、颁发者、序列号 |
| `2.5.29.31` | CRL 分发点 | 4.2.1.13 | URI、理由、CRL 颁发者；明确不在线访问 |
| `1.3.6.1.5.5.7.1.1` | 颁发机构信息访问 | 4.2.2.1 | OCSP、CA Issuers 地址和访问方法 |
| `2.5.29.32` | 证书策略 | 4.2.1.4 | 策略 OID、CPS URI、用户通知文本 |
| `2.5.29.30` | 名称约束 | 4.2.1.11 | permitted、excluded、DNS/邮箱/URI/IP 约束 |
| `2.5.29.9` | 主体目录属性 | 4.2.1.8 | 属性 OID、值和原始编码 |

Issuer Alternative Name（`2.5.29.18`）复用 SAN 的 GeneralName 解码器，也纳入首期。

### 2.2 所有其他扩展的最低保证

任何未知扩展或暂不支持结构化解释的扩展必须显示：

- 中文名称（若 OID 注册表中有名称，否则显示“未知扩展”）。
- 英文标准名称或 `Unknown Extension`。
- OID。
- `critical`：关键 / 非关键，并说明 critical 仅表示该扩展对理解和处理的要求，不等价于“证书不可信”。
- 原始 `extnValue` 十六进制、字节数。
- 若原始值是合法 DER，展示只读 ASN.1 摘要树；无法解析时显示“原始值不是本应用可识别的 DER 结构”，仍保留完整十六进制。

未知扩展不得根据内容猜测语义，也不得因为应用无法解释就生成系统不信任结论。

## 3. 中文语义规则

### 3.1 Key Usage

按 RFC 5280 bit 顺序显示已设置的用途；列表中同时显示中文、英文和 bit 名称：

| bit | 中文 | 说明 |
| --- | --- | --- |
| 0 | 数字签名 | 用于验证签名或生成数字签名 |
| 1 | 内容承诺（不可否认） | 用于内容承诺场景；仅按证书声明展示，不推导法律结论 |
| 2 | 密钥加密 | 用公钥加密或封装密钥 |
| 3 | 数据加密 | 直接使用公钥加密数据 |
| 4 | 密钥协商 | 用于建立或协商共享密钥 |
| 5 | 证书签名 | 用于签发或签署下级证书 |
| 6 | CRL 签名 | 用于签署证书吊销列表 |
| 7 | 仅加密 | 仅在密钥协商语境下表示加密方向 |
| 8 | 仅解密 | 仅在密钥协商语境下表示解密方向 |

摘要示例：`数字签名、密钥加密`。详情区显示每一项的 RFC 解释、bit 编号、是否设置以及原始 BIT STRING 的未使用位数。若扩展为空或编码异常，显示明确的解析状态和原始值。

### 3.2 Extended Key Usage

至少内置以下 OID：serverAuth（服务器身份验证）、clientAuth（客户端身份验证）、codeSigning（代码签名）、emailProtection（电子邮件保护）、timeStamping（时间戳）、OCSPSigning（OCSP 响应签名）、anyExtendedKeyUsage（任意扩展用途）。

其他已知生态 OID 可继续加入注册表，但未知 EKU OID 必须保留点分 OID，不得显示成“无效用途”。

### 3.3 SAN / GeneralName

每一项使用类型化标签显示：DNS 名称、IP 地址、电子邮件、URI、注册 ID、目录名称、其他名称等。IP 地址同时显示规范字符串和原始字节；otherName 暂不猜测内部类型，显示 type-id OID 与原始值。

### 3.4 证书路径和用途的关系

Key Usage、EKU 和 Basic Constraints 是证书声明，不是单独的信任结论。概览页可以显示“声明用途”，但不能写成“适用于当前连接”或“系统已验证该用途”。系统信任结果仍只来自 Security.framework 评估报告。

## 4. Core 数据契约

在 `CertGlassCore` 增加可跨并发边界传递的结构化详情模型，保持 `CertificateExtension.rawValue` 的兼容语义不变（它仍是 extnValue 的内容字节）：

```swift
public enum ExtensionInterpretationStatus: Sendable, Equatable {
    case interpreted
    case rawOnly
    case malformed
}

public struct CertificateExtensionItem: Identifiable, Sendable, Equatable {
    public let id: String
    public let chineseName: String
    public let englishName: String
    public let oid: String?
    public let displayValue: String
    public let rawValue: Data?
    public let children: [CertificateExtensionItem]
}

public struct CertificateExtensionDetail: Identifiable, Sendable, Equatable {
    public let id: String              // OID + occurrence index
    public let oid: String
    public let chineseName: String
    public let englishName: String
    public let critical: Bool
    public let summary: String
    public let interpretationStatus: ExtensionInterpretationStatus
    public let items: [CertificateExtensionItem]
    public let rawValue: Data
    public let rawDERTree: ASN1SummaryNode?
}
```

`ASN1SummaryNode` 放在 Core 时不得依赖 SwiftASN1；它只包含通用的 tag class、tag number、constructed、length、可选显示值和子节点。或者由 Infrastructure 生成 `CertificateField` 树后再映射为同等的 Core DTO，具体实现只能选择一种，不能把 `ASN1Node` 或 Security 类型泄漏到 Core / Features。

`CertificateRecord` 新增 `extensionDetails`，并保证与 `extensions` 按出现顺序一一对应。已有 `fields` 继续用于搜索和复制；扩展字段的 `displayValue` 改为对应 detail 的短摘要。

## 5. Infrastructure 解析设计

在 `StandardCertificateParser` 中分离三层职责：

1. 从 extnValue 解码已知扩展，生成结构化 detail 和短摘要。
2. 对未知 OID 只做通用 DER 摘要，不解释业务语义。
3. 所有失败都保留原始值，并将扩展 detail 标为 `rawOnly` 或 `malformed`；不影响同一证书其他字段展示。

建议按扩展族拆成纯值解码器，统一返回 `CertificateExtensionDetail`：

- `KeyUsageDecoder`
- `ExtendedKeyUsageDecoder`
- `GeneralNamesDecoder`（SAN / Issuer SAN / CRL / AIA 复用）
- `AuthorityKeyIdentifierDecoder`
- `BasicConstraintsDecoder`
- `CertificatePoliciesDecoder`
- `NameConstraintsDecoder`
- `RawExtensionDecoder` 与通用 ASN.1 摘要器

所有 decoder 只接收 `Data` 和 OID 上下文，不访问 Security.framework，不联网，不安装证书，不改写原始 DER。每个扩展出现多次时使用 occurrence index 生成稳定 ID，不能用 OID 作为唯一键。

## 6. 界面设计

### 6.1 详细信息页：Windows 能力的 macOS 原生映射

保留当前“概览 / 详细信息 / 证书路径”三页结构。详细信息页改为 `VSplitView` 或纵向自适应布局：

- 上部：字段列表，显示“字段 / 值”两列。
- 下部：选中字段的详情面板；窗口变窄时允许切换为 `NavigationSplitView`。
- 左上保留搜索；增加筛选：全部、标准扩展、关键扩展、未知扩展。
- 字段分组：证书基本字段、算法与公钥、扩展、签名与原始值。
- 扩展行显示中文名、英文名、critical 徽标和短摘要；未知扩展显示 OID。
- 详情面板分为“解释”和“原始值”两块：解释显示结构化树和中文说明，原始值显示 OID、critical、字节数、十六进制和可复制按钮。
- 复制操作保留现有“复制值 / 复制完整条目 / 复制原始十六进制”，对嵌套条目增加复制当前条目。

不复制 Windows 的“安装证书”“编辑属性”按钮。CertGlass 继续只读，不写钥匙串、不修改信任设置。

### 6.2 概览页增强

在当前截图的主体、颁发者、序列号和有效期下方增加“声明用途”卡片：

- 证书类型：CA / 终端实体 / 无法确定。
- 密钥用法：中文摘要及“查看详细信息”跳转。
- 扩展密钥用法：中文摘要及未知 OID 数量。
- SAN：DNS / IP / URI 数量和前几项，完整内容在详细信息页查看。

该卡片必须标注“证书声明”，避免与系统信任结论混淆。

### 6.3 证书路径页

路径节点详情复用同一 `CertificateDetailsView` 的详情模型，至少显示该节点的 Key Usage、EKU、Basic Constraints 和 SAN 摘要，避免路径页与详细信息页解释不一致。

## 7. 错误和安全边界

- 已知扩展编码非法：显示“扩展编码异常”，保留原始值；不把整张证书标记为损坏，除非证书外层 DER 本身非法。
- 未知 critical 扩展：保留现有 parser warning，但文案改为“应用未实现该扩展的语义解释；这不等同于系统已拒绝该证书”。
- CRL / AIA 中的 URI 只展示，不提供点击联网；可复制 URI。页面显示“本应用不会访问该地址”。
- 不解析或输出私钥；扩展中的 otherName、directoryName 和策略通知只展示证书公开内容。
- 原始 DER、扩展原始值和指纹保持不可变；所有格式化均为展示层派生数据。

## 8. 测试与验收

### 8.1 单元测试

- Key Usage 覆盖每个 bit、组合 bit、空 bit string、未使用位和异常 DER。
- EKU 覆盖已知 OID、anyExtendedKeyUsage、重复 OID 和未知 OID。
- SAN 覆盖 DNS、IPv4、IPv6、邮箱、URI、registeredID、directoryName、otherName。
- Basic Constraints 覆盖 CA、pathLen、缺省值和异常编码。
- SKI / AKI 覆盖 keyIdentifier、authorityCertIssuer、authorityCertSerialNumber。
- CRL DP、AIA、Policies、Name Constraints 至少覆盖一个完整样本和一个 raw-only / malformed 样本。
- 未知扩展验证 OID、critical、原始字节和 DER 摘要均保留。
- 同一 OID 多次出现时 detail ID 和字段 ID 唯一且顺序稳定。

### 8.2 UI 验收

- 打开截图中的真实 `.cer` 后，详细页可看到至少 Key Usage、EKU、SAN、SKI/AKI、CRL DP 或 AIA（以证书实际包含项为准）。
- 选中“密钥用法”能看到“数字签名 / 密钥加密 / 数据加密”等中文解释、bit 状态和原始值。
- 选中未知扩展能看到 OID、critical、原始十六进制和可展开的 DER 摘要（若可解析）。
- 搜索中文名、英文名、OID、摘要和值都能定位字段。
- 详细信息页的解释不改变概览页的信任结论；无网络请求、无钥匙串写入。
- macOS 13+、窗口缩放、无扩展、扩展损坏和算法部分解析状态均有可读的空状态。

## 9. 交给其他 agent 的实施拆分

### Agent 1：Core 契约与扩展注册表

先阅读 `AGENTS.md`、`README.md`、本文件和 `doc/开发交接.md`。新增扩展 detail DTO、解释状态、ASN.1 摘要 DTO；扩展 `CertificateRecord`；补齐 OID 中文/英文注册表和 Key Usage/EKU 语义。不得导入 SwiftASN1、Security 或 SwiftUI。先写 Core 行为测试。

### Agent 2：Infrastructure 扩展解码

实现已知扩展 decoder 和通用 raw-only DER 摘要器，接入 `StandardCertificateParser`，保持原始 DER 和 extnValue 不变。不得联网、访问钥匙串或改变信任评估。先补真实夹具或最小 DER 行为测试，再运行解析器全量测试。

### Agent 3：SwiftUI 详细信息交互

根据本文件实现字段分组、搜索筛选、选中详情、解释 / 原始值面板、复制和概览“声明用途”卡片。Features 只能依赖 Core，不得直接调用 ASN.1 或 Security API。路径节点复用详情组件。

### Agent 4：联调与验收

检查 `ScaffoldServices.make()`、所有测试夹具、README 和 `doc/开发交接.md` 的状态；运行 `swift test`、release build 和应用级人工验收。报告真实证书字段、窗口缩放、未知扩展、离线行为和未验证范围。未经用户要求不要提交 Git。

## 10. 完成定义

当且仅当：常用扩展能以中文结构化展示；未知扩展不丢 OID、critical、原始值和可用的 DER 摘要；详情页支持选择、解释、复制和搜索；信任结论与字段解释保持分离；相关测试和构建验证通过，且交接文档已记录实际完成项与限制，才可把本需求标记为完成。
